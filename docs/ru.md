# Dotfiles и Инструменты Разработки

Этот репозиторий содержит конфигурационные файлы (dotfiles) и скрипты для автоматической настройки рабочего окружения разработчика. Поддерживаются macOS и Linux (через Docker для тестирования).

## Содержимое репозитория

### Конфигурационные файлы
- `.zshrc` - конфигурация оболочки Zsh
- `.vimrc` - настройки Vim
- `.vim/colors/digitable.vim` - цветовая схема Vim в палитре портала [Digitable Courses](https://courses.digitable.life). Ставится в `~/.vim/colors/`; подключается из `.vimrc` командой `colorscheme digitable`. Раскладка по ролям (ключевое слово, строка, комментарий) - из единственной таблицы подсветки портала, поэтому код в Vim выглядит так же, как в блоке кода на его странице
- `.tmux.conf` - конфигурация Tmux
- `.alacritty.toml` - настройки терминала Alacritty, цвета - палитры Digitable
- `.gitconfig` и `.gitignore` - глобальные настройки Git
- `.editorconfig` - настройки форматирования кода
- Конфигурации для различных утилит в `.config/`:
  - `bat` - тема `digitable.tmTheme` для bat и delta. Обе программы берут пользовательские темы из `~/.config/bat/themes`, но видят их только после `bat cache --build`, который делает установщик
  - `bpytop` - мониторинг системы; тема `digitable.theme` и `bpytop.conf`, который её выбирает (без него файл темы лежал бы мёртвым грузом)
  - `lf` - файловый менеджер; `colors` — палитра Digitable в его собственном формате, `lfrc` — то, чего цветами имён не задать: приглашение, строка под курсором, рамка, отметки. Оба файла lf читает сам; `~/.lfrc` он не читает никогда
  - `tmux` - конфигурации сессий
  - `vifm` - файловый менеджер в стиле Vim; `colors/digitable.vifm` — цветовая схема, `vifmrc` включает её строкой `colorscheme digitable`. У каждой группы задано и 256-цветное значение, и 24-битное: vifm выбирает по тому, что объявил терминал
- `.digit/config.yaml` - настройки Digit CLI: локальный провайдер моделей с OpenAI-совместимым интерфейсом, `display.skin: digitable` (скин digit несёт в себе, здесь закреплено только имя) и `skills.external_dirs`, которым digit направляется в общий каталог навыков. Ставится в `~/.digit/config.yaml`; секреты живут в `.env` и здесь не хранятся
- `configs/tools.json` - конфигурация инструментов для интерактивного режима установки

### Палитра
Один набор из семнадцати цветов красит Vim, bat, delta, Alacritty, tmux, bpytop, lf, vifm, eza, GNU ls, строку подсказки zsh и три плагина Logseq. Источник у него один - спека `theme/digitable.flang`: там объявлены сами цвета, раскладка девяти ролей подсветки и пороги контраста, и там же лежат проверки. `scripts/check-theme.sh` сверяет с ней дерево: каждый цвет в конфигах обязан быть либо объявлен в спеке, либо получаться из неё подмесью «цвет N% поверх фона», а каждый объявленный цвет - где-то использоваться. Цвет в дереве записан двумя способами — `#rrggbb` и 24-битной формой ANSI `38;2;R;G;B`, которой пользуются lf и `EZA_COLORS`, — и проверка читает оба. `LS_COLORS` при этом не пишется второй раз: `.zshrc` собирает его из файла цветов lf, формат которого ровно `LS_COLORS`, — двум спискам разъехаться негде. Контраст по WCAG 2.1 считает сам flang (`flang check theme/digitable.flang`); если компилятора на машине нет, проверка честно печатает «не мерил», а не «ок», — а сам `flang` установщик умеет поставить, так что машину есть чем довести до измерения.

Светлые значения двух плагинов Logseq остаются чужими намеренно: палитра Digitable тёмная, светлого набора поверхностей в ней нет. `check-theme.sh` перечисляет эти три значения пофайлово и говорит о них вслух, а не проходит мимо.

### Навыки
- `skills/` - семь навыков без привязки к поставщику (`master-prompt-builder`, `umbrella-repository-setup`, `cluster-agent-setup`, `bilingual-documentation`, `tool-section-page`, `write-post`, `state`). В имени каталога нет вендора намеренно: одни и те же `SKILL.md` и `references/` читают Codex, Claude Code и digit

### Скрипты
- `install-tools.sh` - основной скрипт установки
- `install-skills.sh` - раскладывает `skills/` в один общий каталог и направляет туда клиентов
- `check-configs-install.sh` - берёт из `install-tools.sh` саму функцию `install_configs`, запускает её с подставным `HOME` и убеждается, что каждый файл из `configs/` доехал до домашнего каталога. Список копирования там набран построчно, и новый конфиг по умолчанию не ставится - эта проверка ловит забытую строку. `--selftest` выкидывает одну строку и показывает, что проверка от этого падает
- `check-theme.sh` - сторож палитры Digitable во всех конфигах; `--selftest` подсовывает чужой цвет и показывает, что проверка падает
- `check-vim-quiet.sh` - сторож тишины Vim: ИИ-помощник `vim-ollama` помечен в `.vimrc` как `{ 'on': [] }` и при старте не грузится, поэтому не спрашивает про мастер настройки, не забирает `<Tab>` у coc и не ходит в модель на каждое нажатие клавиши. Проверка гоняет настоящий `vim` с настоящим `configs/.vimrc` в подставном `HOME` и меряет три прогона: обычный старт (плагина быть не должно), `VIM_OLLAMA=1` и `:OllamaOn` на ходу (плагин обязан включиться - иначе выключатель бутафорский). `--selftest` возвращает жадную загрузку и показывает, что проверка падает
- `check-state-report.sh` - проверяет отчёт о состоянии по `skills/state/SKILL.md`: головка не длиннее 14 строк и 900 знаков, от трёх до шести ключевых результатов, у каждого порог, факт и один из `✓ ✗ ?`, затык и запрос на месте, принятое на веру не засчитано достигнутым. `--selftest` показывает, что сам проверяльщик падает на восьми заготовленных случаях
- Пользовательские скрипты в `scripts/customs/`
- Скрипты для lf в `scripts/lf/`
- `tmux.sh` - скрипт для управления сессиями tmux
- `workbench-configs.sh` - раскладывает открытые конфиги Digitable Workbench, забирая их по публичному URL (сами темы в этом репозитории не хранятся)
- `install-codex-skills.sh` - устанавливает все Codex-скиллы из `codex/skills/` в `${CODEX_HOME:-$HOME/.codex}/skills`; раздел о них в README написан как инструкция агенту, которую можно дать ему как есть
- `codex/skills/` - сами семь переносимых скиллов, по каталогу на каждый: `umbrella-repository-setup`, `master-prompt-builder`, `cluster-agent-setup`, `bilingual-documentation`, `tool-section-page`, `write-post`, `state`. Установщик читает этот каталог, поэтому новый скилл не требует правки скрипта. Когда какой применять и в каком порядке - таблица в основном README

## Основные возможности

### Инструменты разработки
- Современные альтернативы стандартным утилитам (eza, bat, ripgrep и др.)
- Инструменты для разработки (Git, Python, Node.js, asdf и др.)
- Файловые менеджеры (lf, vifm)
- Терминальные утилиты (tmux, Alacritty)
- Поддержка различных языков программирования
- digitwm - оконный менеджер: на Linux/BSD собирается из исходников сборка X11 (форк cwm), на macOS ставится лентовая сборка из крана `digitable-lol/tap`, и ей нужно разрешение Accessibility, которое даёт человек
- digitdisk - отчёт о диске и системе: куда делось место и как себя чувствует машина; только читает
- flang - проверяемый язык, на котором написана спека темы; им же `make check-theme` меряет контраст, а без него проверка печатает «не мерил»

### Конфигурация
- Настроенный Zsh с Oh My Zsh и Powerlevel10k
- Vim с плагинами для разработки; ИИ-помощник (`vim-ollama` поверх LM Studio на `localhost:1234`) включается по требованию - `\i`, `:OllamaOn` или `VIM_OLLAMA=1 vim`, - а сам при старте не грузится и в сеть не ходит
- Tmux с оптимизированными настройками
- Интеграция Git с улучшенным выводом

## Установка

### Прямая установка (macOS)

1. Клонируйте репозиторий:
   ```bash
   git clone https://github.com/the-homeless-god/dotfiles.git ~/dotfiles
   ```

2. Запустите скрипт установки:
   ```bash
   cd ~/dotfiles/scripts
   ./install-tools.sh
   ```

3. Следуйте интерактивным подсказкам для:
   - Выбора языка интерфейса (русский/английский)
   - Выбора компонентов для установки
   - Установки конфигурационных файлов
   - Выполнения пост-установочных настроек

### Интерактивный режим установки

Для более детального контроля над процессом установки используйте интерактивный режим:

```bash
./install-tools.sh --interactive
```

Этот режим предоставляет удобный интерфейс с чекбоксами для выбора:
- Категорий инструментов (разработка, медиа, контейнеры и т.д.)
- Отдельных программ внутри каждой категории

Вы можете легко выбрать только те инструменты, которые вам нужны, без необходимости отвечать на множество отдельных вопросов.

### Общий каталог навыков

Навыки из `skills/` ставятся один раз, в `~/.ai/skills`, и каждый клиент
направляется в этот единственный каталог:

```bash
./scripts/install-skills.sh --dry-run
./scripts/install-skills.sh
```

| Клиент | Как добирается до общего каталога |
| --- | --- |
| Codex | `${CODEX_HOME:-$HOME/.codex}/skills` становится ссылкой на `~/.ai/skills` |
| Claude Code | `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/skills` становится ссылкой на `~/.ai/skills` |
| digit | `skills.external_dirs` в `~/.digit/config.yaml` перечисляет `~/.ai/skills`, только на чтение |

Ссылки нужны Codex и Claude Code потому, что ни у одного из них нет настройки
для каталога навыков отдельно: `CODEX_HOME` и `CLAUDE_CONFIG_DIR` переносят весь
дом клиента, а `--add-dir` приходится повторять при каждом запуске. digit в
ссылке не нуждается - он и так умеет читать внешние каталоги навыков.

По умолчанию скрипт связывает каждого клиента, чей домашний каталог уже есть.
Выбрать одного - `--target codex`, `--target claude` (можно повторять) или
`--target none`; перенести общий каталог - `--destination DIR` или `AI_HOME`.

Ничего не затирается. Если в каталоге навыков клиента уже лежат свои файлы,
скрипт отказывается и не меняет ничего; с `--replace` он сначала уносит этот
каталог в резервную копию с отметкой времени рядом, печатает, что унёс, и лишь
затем создаёт ссылку. Резерв переносится, а не удаляется.

**Цена общего каталога.** Все клиенты теперь зависят от одной папки. Снесите или
переименуйте `~/.ai/skills` - и они разом останутся без навыков, тогда как три
отдельные копии потеряли бы одну. Это сознательный обмен: три копии расходятся,
и навык, поправленный в одном месте, остаётся сломанным в двух других. Резервную
копию делайте с `~/.ai`, а не с каталогов клиентов.

### Тестирование в Docker

1. Соберите образ:
   ```bash
   docker build -t dotfiles-test .
   ```

2. Запустите контейнер:
   ```bash
   docker run -it dotfiles-test
   ```

### Использование Docker

#### Использование готового образа

Мы публикуем готовые Docker образы в GitHub Container Registry:

```bash
# Запуск контейнера
docker pull ghcr.io/the-homeless-god/dotfiles:latest
docker run -it --name dotfiles ghcr.io/the-homeless-god/dotfiles:latest

# Для повторного подключения к контейнеру
docker start dotfiles
docker exec -it dotfiles /bin/bash
```

#### Локальная сборка

Если вы хотите собрать образ локально:

```bash
# Сборка и запуск контейнера
docker build -t dotfiles-test .
docker run -it --name dotfiles-dev dotfiles-test

# Для повторного подключения к контейнеру
docker start dotfiles-dev
docker exec -it dotfiles-dev /bin/bash
```

## Структура конфигурации

### Терминал
- **Alacritty**: Современный терминал с GPU-ускорением
- **Tmux**: Мультиплексор терминала с кастомными привязками клавиш
- **Zsh**: Настроенная оболочка с автодополнением и подсветкой синтаксиса

### Редакторы
- **Vim**: Настроен для разработки с различными плагинами
- **VS Code**: Поддержка синхронизации расширений

### Файловые менеджеры
- **lf**: Современный файловый менеджер в стиле ranger, покрашен в палитру Digitable
- **vifm**: Файловый менеджер с привязками клавиш в стиле Vim, покрашен в палитру Digitable

### Утилиты разработки
- **Git**: Расширенная конфигурация с алиасами и интеграциями
- **asdf**: Управление версиями языков программирования
- **Python**: Настроенное окружение с pip
- **Node.js**: Установка через nvm с основными инструментами

## Кастомизация

1. Форкните репозиторий
2. Измените конфигурационные файлы под свои потребности
3. Добавьте или удалите инструменты в `install-tools.sh`
4. Настройте свои пользовательские скрипты в `scripts/customs/`

## Поддержка языков

- Русский (основной)
- English (альтернативный)

Локализация настраивается через `scripts/locales.json`

## CI/CD

Этот репозиторий использует GitHub Actions для непрерывной интеграции и доставки:

- Автоматическая сборка Docker образов при каждом пуше в основную ветку
- Автоматические релизы при создании тегов
- Публикация образов в GitHub Container Registry
- Кэширование сборок для ускорения процесса
- Автоматизированная система тегов

### Автоматические сборки

Следующие события запускают сборку:
- Пуш в основную ветку
- Создание тегов (vX.Y.Z)
- Пулл-реквесты

### Теги Docker

Доступные теги в реестре:
- `latest` - Последняя стабильная версия
- `vX.Y.Z` - Конкретные версии релизов
- `main` - Последняя версия из ветки разработки
- `sha-XXXXXXX` - Сборки конкретных коммитов

### Реестр

Образы публикуются в GitHub Container Registry (ghcr.io):
```bash
ghcr.io/the-homeless-god/dotfiles
```

### Статус сборки

Вы можете проверить текущий статус сборки на [вкладке Actions](https://github.com/the-homeless-god/dotfiles/actions) или по бейджу вверху README.
